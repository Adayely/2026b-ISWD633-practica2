# COMPLETAR  
Antes de esta práctica sabía usar imágenes ya hechas, como nginx o WordPress, pero no tenía claro cómo se construyen ni cómo se controlan los recursos que consume un contenedor. Después de hacerla entendí que se pueden limitar la memoria y la CPU con opciones como --memory, --memory-swap, --cpus y --cpuset-cpus, para evitar que un contenedor consuma todos los recursos del equipo y afecte a los demás. Por ejemplo, con --memory=300m --memory-swap=1g el contenedor puede usar hasta 724 MB de swap. También aprendí que un healthcheck permite que Docker verifique periódicamente si la aplicación funciona de verdad, y lo comprobé cuando mi contenedor de nginx apareció como healthy en docker ps.

Aprendí a escribir un Dockerfile con las instrucciones FROM, RUN, COPY, EXPOSE y CMD, y a construir imágenes con docker build. Comprobé que cada instrucción que crea una capa se ejecuta como un paso (en mi caso 5 pasos, de [1/5] a [5/5]) y que Docker reutiliza las capas que no cambiaron mediante la caché, lo que acelera mucho las construcciones posteriores. De ahí entendí que el orden de las instrucciones importa: lo que cambia con más frecuencia, como el COPY del código, debe ir al final. También aprendí que la opción -P publica los puertos expuestos en un puerto aleatorio del host (en mi caso el 32768), y conocí las imágenes huérfanas y cómo eliminarlas con docker image prune.

Durante la práctica tuve varios errores que me enseñaron bastante. El primero fue que docker build indicaba failed to read dockerfile: no such file or directory. Con dir descubrí que Notepad había guardado el archivo como Dockerfile.txt, así que Docker no lo encontraba, y lo resolví renombrándolo con ren Dockerfile.txt Dockerfile. Aprendí que el Dockerfile debe llamarse exactamente así, sin extensión, y que conviene verificar el nombre y el tamaño del archivo antes de construir. Ese mismo error hizo que docker inspect dijera que la imagen no existía, porque la construcción nunca había terminado.

El segundo error apareció al construir la imagen: yum update falló con Could not resolve host: mirrorlist.centos.org. Esto ocurre porque CentOS 7 llegó al final de su vida útil y sus repositorios originales fueron retirados. Lo resolví agregando un RUN sed que cambia las URLs de los repositorios a vault.centos.org, donde se conserva el archivo histórico. Además, aprendí que ese comando debía ir justo después de FROM, y no al final del Dockerfile, porque tiene que ejecutarse antes de usar yum. Con esto entendí que las instrucciones se ejecutan en orden y que usar imágenes base sin soporte puede traer problemas, por lo que en proyectos reales conviene elegir imágenes mantenidas y leer los mensajes de error completos para encontrar la causa.
